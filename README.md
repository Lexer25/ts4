# TS4 — изменения

Версия: **1.0.3.9** (свойство `Version` в `TS4.csproj`)
Дата: 26.10.2026

Документ описывает правки, сделанные в исходном коде. Существующий `README.md`
(инструкция по установке и регистрации службы) не изменялся.

---

## 1. Сборка и разрядность

| Файл | Изменение |
|---|---|
| `TS4.csproj` | `<PlatformTarget>x86</PlatformTarget>` — сборка всегда 32-битная |

**Причина.** Провайдер `Microsoft.Jet.OLEDB.4.0` существует только в 32-битном виде.
Обычная сборка `AnyCPU` на 64-битной ОС давала x64-процесс, в котором открытие Access
падало с `The 'Microsoft.Jet.OLEDB.4.0' provider is not registered on the local machine`.
Проверено: PE-заголовок собранного `TS4.exe` — x86, из x86-процесса `TS2.mdb`
открывается (18 устройств), из x64 — ошибка провайдера.

| Файл | Изменение |
|---|---|
| `Program.cs` | при старте: если процесс 64-битный, а в конфиге Jet — предупреждение в лог и консоль |

## 2. Конфигурация и параметры запуска

| Файл | Изменение |
|---|---|
| `appsettings.json` | `"isTest": false` (было `true`), уточнён комментарий |
| `WorkerOptions.cs` | новый класс `WorkerTime`: `IsValid()` / `ParseOrDefault()` для формата `H:M:S` |
| `Worker.cs` | конструктор разбирает `timeout` через `WorkerTime`, без `int.Parse` и исключений |
| `Worker4.cs` | `timeout` в `RestartTimeoutTimer` — через `WorkerTime`; сравнение `mode` без NRE |
| `Program.cs` | `GetSection("Service").Get<WorkerOptions>() ?? new WorkerOptions()` — singleton не может быть null |
| `Program.cs` | при старте в лог пишутся версия, `isTest`, `mode`, интервал |

**Причина.** Отсутствие или опечатка в `timeout` роняли конструктор `Worker`
(а он — зависимость `Worker4`), из-за чего служба не запускалась вовсе. Теперь при
неверном значении выводится сообщение и используется значение по умолчанию — 5 минут,
режим — `async`.

`isTest: true` означает, что драйвер не вызывается и на каждую команду возвращается
`ERR`: карты помечаются ошибкой и навсегда остаются в очереди. Для эксплуатации
должно быть `false`; фактический режим теперь виден в логе при любом уровне логирования.

## 3. Работа с COM-драйвером контроллера

| Файл | Изменение |
|---|---|
| `COM.cs` | после таймаута объект помечается «брошенным» (`Abandon`), повторно не используется |
| `COM.cs` | `COM` реализует `IDisposable`, освобождение через `Marshal.FinalReleaseComObject` |
| `COM.cs` | `GetLastDriverResponse` не обращается к брошенному объекту |
| `TSMethods.cs` | `using var com = new COM(...)` — детерминированное освобождение |
| `COM.cs` | удалён отладочный `Console.WriteLine("50", isTest)` |

**Причина.** `Task.Run(...).Wait(timeout)` не прерывает вызов внутри драйвера. Старый код
продолжал работу с тем же COM-объектом (и читал его свойства), пока предыдущий вызов
ещё выполнялся, — одновременный вызов из другого потока даёт `AccessViolationException`,
который в .NET не перехватывается и роняет процесс.

**Изменение поведения.** При таймауте обработка устройства в этом цикле прекращается
(ответ `ERR TIMEOUT`), сырой текст `udprecv` в `load_result` больше не добавляется —
это осознанный обмен: раньше именно чтение свойств зависшего объекта было источником
падения.

## 4. Access (MDB)

| Файл | Изменение |
|---|---|
| `DBAccess.cs` | `GetDataSourcePath()` — путь к MDB из строки подключения |
| `DBAccess.cs` | `CheckTempFolder()` — проверка доступности каталога временных файлов |
| `Worker4.cs` | в `card_in_dev` до открытия: проверка пути, наличия файла и TEMP (сообщения `504`) |
| `Worker4.cs` | в сообщение об ошибке OleDb добавлены путь к MDB и `TEMP` |
| `Program.cs` | те же проверки при старте — в режиме службы иначе не видны |
| `Worker4.cs` | Trace-вывод списка устройств, найденных в Access (строки `508`), перед `510` |

**Причина.** `OleDbException 0x80004005 «Неопознанная ошибка»` не содержит ни пути, ни
причины. Воспроизведено: тот же текст возникает, когда Jet не может пользоваться
каталогом TEMP (типично для службы под учётной записью без загруженного профиля).
Другие случаи дают отдельные тексты: несуществующий путь — «задает ошибочный путь»,
занятый файл — «файл уже используется», битый файл — «Нераспознаваемый формат базы данных».

Теперь при проблеме в логе явно указано, что именно не так: путь к MDB, наличие файла,
состояние TEMP.

Список устройств (уровень Trace) выводится только при включённом `Trace`
(проверка `logger.IsEnabled`), поэтому на боевом уровне логирования накладных расходов нет.

## 5. Firebird

| Файл | Изменение |
|---|---|
| `DBFirebird.cs` | `UpdateIdxCard`: `load_result` и `id_cardindev` передаются параметрами |

**Причина.** Раньше ответ контроллера подставлялся в SQL как текст. Апостроф в ответе
ломал запрос — карта не удалялась из `cardindev` и обрабатывалась бесконечно; кроме того,
это была точка SQL-инъекции из данных устройства. Проверено на рабочей базе
(Firebird 1.5): параметризованный `UPDATE` выполняется, значение с апострофами
и кавычками сохраняется и читается без искажений.

## 6. Логирование

| Файл | Изменение |
|---|---|
| `DateRollingFileSink.cs` | `Emit` обёрнут в `try/catch`: ошибка записи не роняет процесс, уходит в `SelfLog`, файл переоткрывается |
| `Program.cs` | версия программы выводится в первой строке консоли и в стартовой строке лога |
| `Program.cs` | `P1 Файл Access не найден: <путь>` и сообщение о недоступном TEMP при старте |

**Причина.** Исключение из синка логов (нет папки, нет прав, файл занят, диск заполнен)
вылетало в вызывающий код и могло уронить службу — причём именно в тот момент, когда
логи нужны для разбора.

## 7. Потоки и остановка службы

| Файл | Изменение |
|---|---|
| `Worker4.cs` | потоки устройств создаются с `IsBackground = true` |

**Причина.** Потоки по умолчанию — foreground, поэтому зависший вызов контроллера
не давал процессу завершиться: остановка службы упиралась в таймаут SCM.

**Изменение поведения.** При остановке службы незавершённые потоки устройств
обрываются вместе с процессом; карта остаётся в `cardindev` и будет отправлена
в следующем цикле (`writekey` идемпотентен).

## 10. Что осталось сделать

1. **Объекты БД.** В базе `C:\Program Files (x86)\Cardsoft\DuoSE\Access\ShieldPro_rest.gdb`
   отсутствуют процедура `CARDINDEV_TS4` и триггер `CARDINDEV_AI0` (проверено запросами:
   есть только `CARDINDEV_GETLIST`; триггеры `CARDINDEV_BI`, `CARDINDEV_AI` (неактивен),
   `CARDINDEV_BD`). Без них `GetComandForDevice` падает с `Procedure unknown` и ни одна
   карта не обрабатывается. Нужны скрипты `create procedure` / `create trigger` и их
   выполнение на базе; проверку при старте стоит сделать блокирующей.
2. **Уровень логирования.** В конфиге `"LogLevel": "Critical"` → в файл не попадают
   `Warning` и `Error`. Плюс в лог пишется строка подключения Firebird с паролем
   (`Worker4`, сообщение `97`) — пароль следует убрать.
3. **Неиспользуемые настройки.** `maxThreads`, `deviceStaggerMs`, `devicePauseMs`,
   `deviceCommandDelayMs` объявлены, но в `Worker4` не читаются; ограничения числа
   потоков нет.
4. **`ReloadOnChange`.** Перезагрузка `appsettings.json` на лету не работает: провайдер
   в `JsonWithCommentsConfigurationProvider.cs` не удерживает `PhysicalFileProvider`
   и не использует `ChangeToken.OnChange`. Изменения применяются только после перезапуска.
5. **Мёртвый код.** `Worker` (создаётся, но не запускается), `Worker2`/`WorkerTest`,
   `Worker3`, `ArtonitHttp`, `ArtonitUdp`, `SerilogRollingHostedService`,
   `BatchSuccess`/`BatchFail`, `StatInsert*`, проекты `ControllerStatistics*`.
